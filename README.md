# 구독 결제 서비스

## 문제 정의
외부 결제사 호출은 타임아웃이 나면 결제가 됐는지 알 수 없다.
이때 실패로 처리하면 돈은 나갔는데 구독은 끊기고, 다시 결제하면 이중 청구가 된다.
이 프로젝트는 결과를 모르는 결제를 상태 조회로 확정해서, 장애 상황에서도 청구를 정확히 유지하는 것이 목표다.

## 성공 지표
Mock PG의 타임아웃 비율을 0%, 30%, 50%로 높여도 아래를 유지한다.
1. 중복 청구 0건: 구독의 한 결제 주기에 실제로 청구된 결제는 최대 1건
2. 재전송 기한(24시간) 이내 미확정 0건: 확정 잡 실행 후 기한 안에서 UNKNOWN으로 남은 결제 없음
3. 기록 불일치 0건: 우리 DB의 승인 목록과 결제사 승인 목록이 일치

### 4역할 설계 토론
| 설계 | 이상주의자 제안 | 비관론자 지적 | 현실주의자 판단 | 최종 결정 |
|---|---|---|---|---|
| 결제 1건 흐름 (결제 기록, 결제사 호출, 결과 반영, 확정 잡) | 청구 의도와 결제 시도 테이블 분리, 상태 7개, 호출 기록 테이블, 행 단위 선점(lease) | 포기한 시도 뒤의 새 시도와 승인 기록을 거부하는 제약이 이중 청구 경로, 결과 반영 중 예외를 실패로 해석하면 이중 청구 | 테이블 1개와 UNIQUE(charge_key), 상태 4개에 FAILED에서 APPROVED 허용, 결과 반영 실패는 Pending 반환, 거절 허용 목록만 MVP에 반영 | 같은 주문번호로만 재전송, 결과 반영 규칙표, attempt_no 제거로 채택. 나머지는 보류 또는 기각 (ADR 0001) |

### 리뷰 에이전트가 잡은 주요 문제
| 문제 | 영향 | 처리 |
|---|---|---|
| 결제 흐름을 바깥 트랜잭션 안에서 호출해도 막는 장치가 없음 (중간 1번) | 승인 뒤 결과 반영이 실패하면 바깥 롤백으로 결제 기록이 사라지고, 같은 chargeKey로 재시도하면 새 주문번호로 두 번째 승인이 나가 이중 청구 | 트랜잭션 안에서 호출하면 결제사를 부르기 전에 예외를 던지도록 수정 (TransactionGuard). 방어 코드를 지우면 실패하는 테스트 추가 |
| 같은 chargeKey에 내용이 다른 요청이 와도 기존 결과를 그대로 돌려줌 (중간 2번) | 금액이 다른 요청에 Approved가 반환되어 호출자가 요청한 금액이 결제된 것으로 오해 | 금액, 고객키, 빌링키를 비교해 다르면 ChargeRequestMismatchException을 던짐. 결제사를 부르기 전이라 청구 없음 |
| 낙관적 잠금, 건별 예외 격리, 재전송 결과 반영에 테스트가 없음 (중간 3번) | 해당 코드를 지워도 모든 테스트가 통과함. @Version이 빠지면 늦은 반영이 먼저 확정된 승인 기록을 덮어씀 | 두 트랜잭션 경합 재현 통합 테스트와 확정 잡 단위 테스트 추가. 각 코드를 지우면 테스트가 실패하는 것을 확인 |
전체: docs/review-log.md
