# 결제 1건 흐름

TX1에서 요청할 결제의 상태를 저장(커밋) → 토스에 결제 요청(트랜잭션 밖) → TX2에서 토스 응답에 따라 상태를 수정

## 알게 된 것
- DB에 결제 상태를 저장해서 추적한다. TX1 기록은 확정 잡의 할 일 목록이자, 같은 청구를 다시 결제하지 않게 하는 표시다.
- 주문번호를 멱등키로 써서 몇 번을 다시 보내도 결제는 한 번만 된다.
- 원래 결제 흐름과 확정 잡이 동시에 같은 결제 행을 고칠 수 있어서, 늦게 온 쪽이 덮어쓰지 못하게 @Version으로 낙관적 락을 건다.
- @Transactional은 같은 클래스 안에서 부르면 프록시를 거치지 않아 무시된다. 그래서 트랜잭션 메서드는 다른 클래스(PaymentWriter)에 두고 밖에서 부른다.
- Unknown은 토스가 주는 답이 아니라 우리가 내리는 판단이다. 타임아웃, 5xx, 처리 중, 처음 보는 코드처럼 확실하지 않은 응답은 전부 Unknown으로 두고 확정 잡이 다시 물어본다.

## Node.js에서는
- 트랜잭션 안에서 외부 API(axios.post)를 부르면 안 되는 건 Node.js도 똑같다. 응답을 기다리는 동안 DB 커넥션을 붙잡고, 롤백되면 결제 기록이 사라진다.
- @Transactional은 queryRunner로 트랜잭션을 열고 커밋, 롤백하는 코드를 메서드에 자동으로 감싸주는 것과 같다.

## 헷갈렸던 것
- 24시간이 지나면?
  → 토스에 기록이 없으면 재전송하지 않고, 계속 Unknown이면 에러 로그를 남긴다. 둘 다 상태는 그대로 두고 사람이 확인한다.
- 토스가 거절했는데 응답이 중간에 사라지면?
  → 결제 기록은 삭제하지 않는다. 확정 잡이 조회해서 거절을 확인하면 FAILED로 바꾼다. 조회 결과가 "주문 없음"이면 같은 키로 재전송하고, 토스가 처음 거절 응답을 그대로 돌려줘서 FAILED가 된다.
- 바깥 트랜잭션 안에서 결제를 호출하면?
  → TX1이 따로 커밋되지 않고 바깥에 합류한다. 토스 승인 후 바깥이 롤백되면 기록이 사라지고, 재시도 때 이중 청구가 된다.
