# 검증한 결제 시나리오

결제사가 어떻게 반응하고 서버가 어느 지점에서 죽어도 중복 청구가 없고 결과가 확정되는지 확인한 시나리오 목록이다.

## 확인 방법

- 모든 시나리오는 실제 `ChargeService`와 `PaymentStatusResolver`를 실제 MySQL(Testcontainers)과 실제 HTTP로 호출하는 Mock PG에 연결해서 실행한다. 위치는 `src/test/kotlin/com/jinseon/billing/charge/scenario/ChargeScenarioTest.kt`다.
- 각 시나리오에서 세 가지를 단언한다.
  - 결제 상태
  - 결제사 호출 횟수 (승인 요청, 조회)
  - 결제사 원장 기준 실제 청구 횟수 (1을 넘으면 이중 청구)
- 시계는 테스트가 직접 조정한다. 확정 잡은 5분 이상 지난 결제만 보므로 확정 잡을 돌리기 전에 시계를 6분 앞당긴다.
- 타임아웃은 클라이언트의 read-timeout을 500ms로 줄이고 Mock PG가 1.5초 늦게 응답하게 해서 재현한다.
- 구독 기능이 아직 없어서 구독 상태는 확인하지 않는다.
- 2026-10-31 기준 전체 테스트 163개가 통과한다.

표에서 승인, 조회, 청구는 각각 결제사에 보낸 승인 요청 횟수, 조회 횟수, 결제사 원장 기준 실제 청구 횟수다.

## 결제사 반응 7가지

| 시나리오 | Mock 설정 | 기대 결과 | 테스트 위치 (ChargeScenarioTest, 결제사 시나리오) |
|---|---|---|---|
| 바로 승인 | `APPROVE_OK`: 승인을 기록하고 200 DONE | 결제 `APPROVED`. 승인 1, 조회 0, 청구 1. 확정 잡을 돌려도 변화 없음 | `결제사가 바로 승인하면 결제는 APPROVED이고 조회 없이 청구는 한 번이다` |
| 카드 거절 | `DECLINED`: 기록 없이 403 `REJECT_CARD_PAYMENT` | 결제 `FAILED`, 거절 코드 반환. 승인 1, 조회 0, 청구 0 | `결제사가 카드를 거절하면 결제는 FAILED이고 청구는 없다` |
| 승인 후 응답 지연 | `TIMEOUT_AFTER_APPROVE`: 승인을 기록한 뒤 응답이 늦어 호출자가 타임아웃 | 호출 직후 `Pending`, `UNKNOWN`. 확정 잡이 조회로 승인을 확인해 `APPROVED`. 재전송 없음. 승인 1, 조회 1, 청구 1 | `타임아웃 후 결제사에 승인 기록이 있으면 재전송 없이 승인으로 확정된다` |
| 요청 유실 | `TIMEOUT_BEFORE_APPROVE`: 아무것도 기록하지 않고 응답만 늦음 | 호출 직후 `Pending`, `UNKNOWN`, 청구 0. 확정 잡이 조회에서 기록 없음을 확인하고 같은 주문번호로 재전송해 `APPROVED`. 승인 2, 조회 1, 청구 1 | `타임아웃 후 결제사에 기록이 없으면 같은 주문번호로 재전송해 승인되고 청구는 한 번이다` |
| 승인 후 서버 오류 | `SERVER_ERROR_AFTER_APPROVE`: 승인을 기록한 뒤 500 반환 | 500을 실패로 보지 않고 `UNKNOWN`. 확정 잡이 조회로 `APPROVED`. 승인 1, 조회 1, 청구 1 | `승인 후 서버 오류 500을 받아도 조회로 승인이 확인되면 승인으로 확정된다` |
| 조회 장애 | `LOOKUP_UNAVAILABLE`: 승인을 기록하고 응답이 늦으며 첫 조회만 503 | 첫 확정 잡은 결과를 알 수 없어 `UNKNOWN` 유지 (승인 1, 조회 1, 청구 1). 두 번째 확정 잡에서 `APPROVED` (조회 2) | `조회가 한 번 실패해도 결제는 UNKNOWN으로 남고 다음 확정 잡에서 승인으로 확정된다` |
| 결제사 처리 중 | `IN_PROGRESS_THEN_DONE`: 처리 중으로 기록하고 응답이 늦음. 테스트가 완료 처리할 때까지 승인되지 않음 | 확정 잡이 처리 중임을 보고 재전송하지 않고 `UNKNOWN` 유지 (승인 1, 조회 1, 청구 0). 완료 처리 뒤 다음 확정 잡에서 `APPROVED` (조회 2, 청구 1) | `결제사가 처리 중이면 재전송하지 않고 기다리다가 완료되면 승인으로 확정된다` |

## 서버가 죽은 지점별 확인

결제 흐름은 결제 기록(TX1), 결제사 호출, 결과 반영(TX2) 순서다. 서버가 어느 지점에서 죽는지에 따라 결제사 원장과 우리 DB의 상태가 달라진다. 확정 잡이 이를 복구한다.

| 크래시 지점 | 결제사 원장 | 우리 DB | 확인하는 것 | 테스트 위치 |
|---|---|---|---|---|
| 1. 결제 기록 전 | 없음 | 없음 | 아무것도 보내지 않았으므로 예외를 그대로 던지고 결제사를 부르지 않는다. 같은 chargeKey로 다시 요청해도 안전하다 | ChargeServiceTest, `결제를 기록하지 못하면 결제사를 부르지 않고 예외를 그대로 던진다` |
| 2. 결제 기록 직후, 호출 전 | 없음 | `REQUESTED` | 같은 chargeKey로 다시 요청하면 결제사를 부르지 않고 `Pending`을 돌려준다. 확정 잡이 조회에서 기록 없음을 확인하고 재전송해 `APPROVED` (승인 1, 조회 1, 청구 1) | ChargeScenarioTest, 서버가 중간에 죽은 경우, `결제 기록 직후 호출 전에 죽었으면 확정 잡이 조회 후 재전송해 승인하고 같은 요청은 결제사를 부르지 않는다` |
| 3. 결제사 호출 후, 결과 반영 전 | 승인됨 | `REQUESTED` | 확정 잡이 조회로 승인을 확인하고 재전송 없이 `APPROVED` (승인 1, 조회 1, 청구 1). 결과 반영 자체가 DB 장애로 실패해도 호출자는 예외가 아니라 `Pending`을 받는다 | ChargeScenarioTest, 서버가 중간에 죽은 경우, `결제사는 승인했는데 결과 반영 전에 죽었으면 확정 잡이 재전송 없이 승인으로 확정한다`. ChargeServiceTest, `결과를 DB에 반영하다 예외가 나도 밖으로 던지지 않고 Pending이다` |
| 4. 결과 반영 후 | 승인, 거절, 알 수 없음 | `APPROVED`, `FAILED`, `UNKNOWN` | `UNKNOWN`만 확정 잡의 대상이다. 확정된 결제에 원래 요청의 늦은 `Unknown` 결과가 와도 승인이 유지된다. 상태 조합 16칸의 반영 규칙은 PaymentWriterTest가 확인한다 | ChargeScenarioTest, 서버가 중간에 죽은 경우, `확정 잡이 승인으로 확정한 뒤 원래 요청의 늦은 Unknown 결과가 와도 승인이 유지된다`. 위 결제사 반응 7가지 중 승인 후 응답 지연, 승인 후 서버 오류, 조회 장애, 결제사 처리 중 |
| 5. 확정 잡이 재전송한 직후, 결과 반영 전 | 승인됨 (죽은 실행의 재전송이 도달) | `REQUESTED` | 다시 실행된 확정 잡이 조회로 승인을 확인하고 다시 보내지 않는다 (승인 1, 조회 2, 청구 1). 이미 확정된 결제는 다음 실행에서 건드리지 않는다 | ChargeScenarioTest, 서버가 중간에 죽은 경우, `확정 잡이 재전송한 직후 결과를 반영하기 전에 죽었다가 다시 실행되면 다시 보내지 않고 승인으로 확정한다`. 조회 장애 시나리오도 재실행 안전성을 확인한다 |

## 그 밖의 시나리오

| 시나리오 | 기대 결과 | 테스트 위치 (ChargeScenarioTest) |
|---|---|---|
| 확정 대기 5분이 지나기 전 | 확정 잡이 건드리지 않는다. `REQUESTED` 유지, 승인 0, 조회 0 | 서버가 중간에 죽은 경우, `기록 직후 죽은 결제도 확정 대기 5분이 지나기 전에는 확정 잡이 건드리지 않는다` |
| 재전송 기한 24시간 정각 | 기한 안이므로 재전송해 `APPROVED` (승인 1, 조회 1, 청구 1) | 서버가 중간에 죽은 경우, `재전송 기한 24시간 정각까지는 재전송한다` |
| 재전송 기한 24시간 초과 | 재전송도 실패 처리도 하지 않고 `REQUESTED` 유지. 승인 0, 조회 1, 청구 0 | 서버가 중간에 죽은 경우, `재전송 기한 24시간이 지난 결제는 재전송도 실패 처리도 하지 않고 그대로 남는다` |
| 결제사 처리 중이라는 응답이 24시간 초과 | `FAILED`로 바꾸지 않고 `UNKNOWN` 유지. `RESOLVE_STUCK` ERROR 로그가 1건 남는다. 승인 1, 조회 1, 청구 0 | 서버가 중간에 죽은 경우, `결제사가 처리 중이라는 응답이 24시간을 넘게 이어지면 FAILED로 바꾸지 않고 ERROR 로그를 남긴다` |
| 같은 chargeKey로 순서대로 두 번 요청 | 결제는 하나이고 결제사 호출도 한 번이다 | 같은 청구를 여러 번 요청하는 경우, `같은 chargeKey로 순서대로 두 번 요청하면 결제는 하나이고 결제사 호출도 한 번뿐이다` |
| 결과를 모르는 결제를 같은 chargeKey로 다시 요청 | 새 승인 요청을 보내지 않고 같은 결제의 `Pending`을 돌려준다 | 같은 청구를 여러 번 요청하는 경우, `결과를 모르는 결제를 같은 chargeKey로 다시 요청해도 새 승인 요청을 보내지 않는다` |
| 같은 chargeKey로 동시에 요청 (6개 스레드) | 결제 행은 하나이고 결제사 승인 요청은 한 번이다. 모든 요청이 같은 결제를 가리킨다 | 같은 청구를 여러 번 요청하는 경우, `같은 chargeKey로 동시에 요청해도 결제는 하나이고 결제사 승인 요청은 한 번뿐이다` |
| 같은 chargeKey에 금액이 다른 요청 | `ChargeRequestMismatchException`을 던지고 기존 결제(9,900원)와 결제사 호출 횟수는 그대로다 | 같은 chargeKey로 다른 내용이 오는 경우, `금액이 다른 요청은 예외로 막히고 기존 결제와 결제사 호출 횟수는 그대로다` |
| 트랜잭션 안에서 `charge()` 호출 | 결제사를 부르기 전에 막힌다. 결제 기록도 청구도 남지 않는다 | 트랜잭션 안에서 호출하는 경우, `트랜잭션 안에서 charge를 부르면 결제사를 부르기 전에 막히고 결제 기록도 남지 않는다` |
| 트랜잭션 안에서 확정 잡 호출 | 결제사를 조회하기 전에 막힌다. 결제 상태는 그대로다 | 트랜잭션 안에서 호출하는 경우, `트랜잭션 안에서 확정 잡을 부르면 결제사를 조회하기 전에 막힌다` |
